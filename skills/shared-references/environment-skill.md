# Project environment

Each machine keeps what its roles need to know about it in two places, both written first by the side's setup role on the real machine and kept current afterwards by the side's memory role:

1. **Facts and lessons: the environment section of `CLAUDE.md`.** Every role reads CLAUDE.md, so every role knows the machine without loading anything. Write it with `node .contrejour/dist/tools/setup-cli.js environment --project . --input <file>` (without `--input` it shows the current section); the helper replaces the whole section between its markers and keeps it under 8000 characters. One line per fact: machines and SSH aliases; code, data, checkpoint, result and log paths; environment names and how to activate them; resources and their limits; where the metric lands; verified pitfalls. Do not explain general tools (conda, ssh, git, screen, pip, CUDA), restate defaults, or record guesses, results or research notes: the section is environment only, because every role reads it, the blank ideator included.
2. **Fixed procedures: the scripts of the project skill `<project>-environment`**, in the directory apply reports as `environment_skill_dir`. Its `SKILL.md` has frontmatter `name: <project>-environment`, a one-line description, and a table of the scripts with their arguments and output; the facts stay in CLAUDE.md. A procedure that runs the same way every time becomes a script, typically: sync code, prepare the environment, launch a named run, check a run, fetch its logs and results, stop it. Write only what this environment needs. Scripts use `#!/usr/bin/env bash` and `set -euo pipefail`, take arguments instead of being edited, read keys and tokens from `.contrejour/environment.json` (never inline them), and give every run its own name, log and result path so several experiments can run at once. A procedure that needs a browser uses [browser-act](../browser-act/SKILL.md) after `node .contrejour/dist/tools/ensure-browser-act.js`; create the browser and any login with the owner while writing the script and record the browser id as a fact, because a script cannot ask for approval. Never use Playwright, Selenium or Puppeteer.

Find out what you can by inspecting the machine; ask the owner only for what you cannot. Run every script once for real; for a launch, use a small, short run of the project's own entry point. Record only what ran. If a script cannot be made to work, report the environment step as incomplete with the real error; do not claim the environment is ready.

Later, when work reveals a new environment fact or a procedure repeated by hand, the memory role adds it the same way: a line in the section or a verified script.
