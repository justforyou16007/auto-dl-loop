# Packaging

Contrejour installs explicitly into projects and runs on Claude Code. This repository contains no Claude Code implementation. It is a project package: it holds what is particular to the research task and builds on two git submodules, the framework `agent-loop-studio/` and the shared library `agent-loop-community/`. The archive and a local installation carry all three, so a target machine needs no submodule, build tools or npm install. User installation and updates live in the [setup guide](../SETUP_GUIDE.md); the archive includes that guide as its README.

## Build

Prepare a checkout explicitly: `git submodule update --init`, `npm ci` and `npm --prefix agent-loop-studio ci`. Then `npm run build:framework` builds the framework in its own directory: its helpers with tsc, and the Studio's page with Vite, into `agent-loop-studio/dist/`. `npm run build` (`tools/build.mjs`) stops if that has not happened; otherwise it copies `agent-loop-studio/dist/` into `dist/` and bundles each research helper (`config-cli`, `validation-cli`, `worker-cli`, `research-wiki`, `capture-filter`, `ensure-browser-act`, and the extension `research-extension`) with esbuild into one file next to the framework's helpers.

Research sources import framework modules as `@studio/tools/…` and `@studio/lib/…` (the tsconfig `paths` map them to `agent-loop-studio/src/`). The bundles keep these as imports of the framework's compiled files beside them, so there is a single copy of the framework, and every helper stays at `.contrejour/dist/tools/<helper>.js` in a project. Commander is the only runtime dependency. The Studio's packages (React, React Flow, Tailwind, Radix, lucide) are build-time dependencies of the framework only: the package carries the built page.

## The archive

Run `npm run pack:contrejour`: it builds, then `tools/pack-contrejour.mjs` writes `artifacts/contrejour-0.1.0.tar.gz` and its `.sha256`. Node.js 22.12+, Bash and tar are host prerequisites. The archive contains:

- the helpers reached from its entrypoints, traced through their local imports in `dist/`: the framework's hook, loop-check, library-cli, loop-view, studio and project-cli, and the research helpers above; plus the Studio's built page, `dist/studio/`;
- the skills: the framework's shared references (`running-loops.md`), then this package's `research-wiki` and `browser-act` skills and shared references;
- one `library/` laid together from the framework's, then the community's over it, then this package's: the community's version of a framework loop or role replaces the framework's file, and each side keeps its folder, so the validator's `contribution-check` lies beside the framework's and the installer gives validator projects their side's own (see Ownership);
- `templates/`, `project.json`, the setup guides, the license, the Commander runtime and a manifest with every file's hash;
- the framework's installer (`install.sh`, `install.mjs`).

Add new runtime entrypoints and shipped skills there, and a new research helper in `tools/build.mjs` too, rather than shipping unrelated tools. The other skills (GPU platforms, literature search, Feishu, Overleaf) stay in the source tree.

The release archive remains available for manual offline distribution and CI; local repository installation does not read or download it. After changing shipped code, roles, loops, skills or documentation, here or by moving a submodule, run `npm run pack:contrejour` and copy the archive and checksum into `distribution/releases/` before committing.

## Installing from a checkout

The normal installation entrypoint is `bash distribution/install-contrejour.sh --role worker|validator --project PATH` from a prepared local Git checkout of this package. `distribution/install-from-repo.mjs` checks that the checkout has `project.json` and its built runtime, and names the preparation steps when a piece is missing. It then runs `tools/pack-contrejour.mjs --directory <temporary-directory>` to assemble the same files as the release, and runs the framework's installer from there with `--library` set to the checkout. It requires no tar and makes no network requests or Git/npm updates. Missing local runtime files stop installation before anything is written.

## Ownership

The installer is the framework's; this package describes itself to it in `project.json`. `--role` names one of its profiles, `worker` or `validator`, and each profile names its entry role (`worker-task-manager`, `validator-task-manager`) and the library side its loops and roles come from. `.contrejour/install.json` records the profile, and an update with another one is refused. It also records the checkout as the project's `library`. There the project later finds loops it does not have yet; where several libraries hold the same name, this package's comes first, then the community's, then the framework's (`librariesFor` in the framework's `src/tools/installation.ts`). What the project improves stays in the project until the owner decides to share it: then `library-contribution` lists the project's new and changed loops and roles, and the ones the owner chooses go, as one pull request, to agent-loop-community (the copy that checkout carries, or one fetched when it carries none). Nothing goes to this package or to the framework.

The installation manifest also records the hashes of managed files. Updates preflight conflicts and replace only owned package files — helpers, runtime, templates, skills and the package's `project.json` — and remove managed files dropped from the package. Loops and roles are seeded instead: the installer writes those every project gets (the libraries' `framework` folders) and those of the profile's side, where a side's file takes the place of the framework's of the same name, and only where the project has none of that name. This package uses that for one loop, the validator's `contribution-check`: its leak review of whatever leaves, in place of the framework's, which puts the files to the owner. Each side's `configure` is the research task's own loop, which the framework does not have. From then on the seeded files belong to the project (`trajectory-optimizer` fixes roles, the owner changes loops through `loop-authoring`), and updates never replace or remove them. A copy of each as seeded stays in `.contrejour/seeded/`, and `project-cli.js use` keeps one the same way for a library loop and the roles it brings in later. That baseline tells what the project changed: a file it left alone is never contributed, a changed one is merged three ways with the community's version when that changed too, and the check of a contribution lays the baselines under the libraries, so a library the project has no checkout of (this package's, for a project installed from an archive) still counts. A seeded file without a baseline, from a project installed before baselines were kept, is never offered: what the project changed in it cannot be told.

The installer writes, through the installed `project-cli.js hooks`, the hooks, the profile's entry role and `worktree.bgIsolation: "none"` in `.claude/settings.json`, replacing only its own entries, so the hooks guard every loop from the first one and every session starts as the side's task manager. Project data, the project environment skill, `.contrejour/environment.json`, the rest of `.claude/settings.json` and unrelated agent configuration survive updates. A project installed for Codex by an earlier release, or by the releases named ARL (data under `.aris/`), is refused rather than migrated.

The installer neither configures the machine nor chooses a loop; what it prints next says what does. Open `claude` in the project once and accept the folder trust prompt. Then each machine takes two loops, one after the other. The side's `configure`, the research task's own (from the Studio, or `claude "Run the configure loop"`), configures the machine and applies the configuration the owner approved (`config-cli.js apply`). The framework's `setup`, which every project has, sets up the project's workflow: the Studio opens a project that is not set up with it, and `claude "Run the setup loop"` runs it too. Its task loop step records the loop the owner approved and its parameter values in `.contrejour/loop.json` (`project-cli.js use`, which the Studio also uses to change them later), and its hand-off records in `.contrejour/setup.json` that the project is set up (`project-cli.js finish-setup`). `config-cli.js apply` and `project-cli.js use` both write the entry role again. Do the validator first: the worker's `configure` fetches `task.md` from the validator's running service, and that service starts only once the validator is configured and its review loop chosen. On the worker, `loop-trial` can then try `research-iteration` for real before the rounds start: its `trial-args` stop the round after Build, before it submits. `submission-review` declares none, since it needs a real submission.

`claude agents` shows the background sessions. Read research records through the wiki skill, CLI or Markdown files. See the [architecture guide](../ARCHITECTURE_GUIDE.md) for the worker/validator trust boundary.
