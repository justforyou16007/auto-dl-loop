# Testing

Use real temporary directories, installed artifacts and the actual helper commands. Test the behavior visible to the worker or project owner. Avoid assertions that mirror implementation details.

Run only the relevant file locally: `npm run test -- tests/test_setup.ts`. Never run the full suite locally or repeat a test another agent has already reported green without a new change or unresolved concern. CI checks out the submodules, installs the dependencies of this package and of the framework and builds the framework; it then checks types, lint and format, packs the archive and runs the library check (`tools/library-check.mjs`: this package's loops and roles with the framework's and the community's laid underneath, as a project gets them), and runs the nine TypeScript suites, one job each. The framework's own suite, `tests/test_project.ts` in agent-loop-studio, runs in that repository: a project of the framework alone, installed with `setup`, `loop-trial` and the framework's other loops and roles (`project-setup` and `loop-tester` among them), its hooks and entry role written at once; `project-cli.js finish-setup` refused until a task loop is chosen; the Studio starting a project from a reference, opening it with its setup loop while it is not set up, refusing a trial of a loop the project lacks, and copying it; its hooks; and its contribution, which waits for a finished task and plans a new role and a changed framework role alike for the community library, with nowhere to go until one is fetched.

These six suites consume compiled helpers, so build first: `npm run build:framework`, then `npm run build`.

- **Installation and configuration** (`test_setup.ts`) exercises both prepared local Git checkouts, with their submodules, and archives. Installation seeds the loops and roles from the framework's, the community's and this package's libraries, the framework's `setup` beside the side's own `configure`, writes the hooks and the entry role at once, and the installed loops and roles pass their checks. Each machine is configured through `config-cli.js`, as the steps of its side's `configure` loop do (the sheet, fetching `task.md`, confirm and apply), which chooses no loop; the task loop and its parameter values are chosen apart from it with `project-cli.js use`, as `setup`'s task loop step does, and the validation service reviews with that choice. Also the settings and CLAUDE.md blocks, and repair, updates and integrity checks from isolated directories. Local installation tests forbid download, npm and tar commands, and verify that missing dependencies or build output cause errors without writing the target.
- **Framework** (`test_framework.ts`): the library's loops and roles as each side's project gets them, the loop and role checks (child loops, loop kinds and drafts included), the hook actions, the check that every answer a loop gets is the owner's own, and the worker's ledger and waiting.
- **Contribution** (`test_contribution.ts`) models the three repositories on local bare repositories standing in for GitHub: the framework's library and the community's, each in its own repository, and this package with both as real submodules. It runs the real installer and git, with a stand-in `gh`. A plan offers the project's new and changed loops and roles, never one it left alone, and the owner chooses among them; all they choose goes to the community library as one pull request, a project's version of a role this package or the framework gave it included, and nothing goes to this package or the framework. A role another project already changed in the community library merges three ways, both changes kept, or stays out as a conflict when both changed the same part; a name the community already holds is not overwritten. Nothing leaves before a task has finished; keys, tokens and hidden paths are blocked and paths of this machine warned about; an owner's own agent, a role of the wrong side, a stale script or a result the library check fails stays out; a plan changed since the owner approved it is refused; what a pull request already carries is not sent again; and on the validator nothing leaves without its own check's pass on that digest. Also forks without write access, `gh` missing or signed out, a checkout without a remote, a community library whose default branch has no library yet, fetching the community library for a project installed from an archive (whose package's loops and roles still stand under the check, through its baselines), and projects installed before baselines were kept, whose seeded files are never offered.
- **Loop view** (`test_loop_view.ts`) installs a worker and a validator project with the real installer and checks what the owner's page shows (the loops with their kinds and sources, `setup`, `loop-trial` and the side's own `configure` among them, and a loop the project removed shown from the library; steps and their roles; the loops a loop runs as steps, `loop-authoring` in `setup` and no `configure` there; parameter values; runs from the trajectory index, no transcript read; neither side seeing the other's loops and roles), the page written as one file (its data cannot close its script, nothing loaded from elsewhere) and the served page (only its own address, read-only).
- **Studio** (`test_studio.ts`) checks the console's server: the one-time sign-in, what a stranger is refused, the loops' kinds (`setup`, the side's `configure` and `loop-trial` among them), the flows it draws from the loops the project got from the library (steps, stages, groups, arrows back, ahead and out, parameters joined to their steps, the loops run as steps, such as `loop-authoring` in the Task loop and Check of setup's four steps (Goal, Task loop, Check, Hand off) and a contribution's own check, and the research round's trial ending after Build, before Submit), the quick search, and the owner's choice of the task loop and its values (values a parameter does not allow, an on-request loop and an unknown one refused; a library loop brought in with the roles it lacks and their baselines).
- **Studio authoring** (`test_studio_authoring.ts`) drives the chat against a stand-in `claude`: the request reaching `loop-authoring` with what the owner pointed at, the review note and the draft drawn when the loop waits, the reply passed on unchanged, and the end.

Review sessions are tested against a stand-in `claude` command. Do not add Claude Code authentication checks to tests. Report the difference between archive and helper verification and a real two-machine deployment with Claude Code. Never restart a running Claude Code background service or Paseo daemon to recover from a test timeout.
