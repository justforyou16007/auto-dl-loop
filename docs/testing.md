# Testing

Use real temporary directories, installed artifacts and the actual helper commands. Test the behavior visible to the worker or project owner. Avoid assertions that mirror implementation details.

Run only the relevant file locally: `npm run test -- tests/test_setup.ts`. Never run the full suite locally or repeat a test another agent has already reported green without a new change or unresolved concern. CI checks out the submodules, installs the dependencies of this package and of the framework and builds the framework; it then checks types, lint and format, packs the archive and runs the library check (`tools/library-check.mjs`: this package's loops and roles with the framework's and the community's laid underneath, as a project gets them), and runs the nine TypeScript suites, one job each. The framework's own suite, `tests/test_project.ts` in agent-loop-studio, runs in that repository: a project of the framework alone, installed with `setup` and the framework's other loops, set up only once a task loop is chosen (`project-cli.js finish-setup`), opened in the Studio with its setup loop and copied, its hooks, and what it shares versus what it sends upstream.

These six suites consume compiled helpers, so build first: `npm run build:framework`, then `npm run build`.

- **Installation and configuration** (`test_setup.ts`) exercises both prepared local Git checkouts, with their submodules, and archives. Installation seeds the loops and roles from the framework's, the community's and this package's libraries, each side's `configure` in place of the framework's beside the framework's `setup`, and writes the hooks and the entry role at once. Each machine is configured through `config-cli.js`, as the steps of its side's `configure` do (the sheet, fetching `task.md`, confirm and apply), which chooses no loop; the task loop and its parameter values are chosen with `project-cli.js use`, as setup's task loop step does. Also the settings and CLAUDE.md blocks, and repair, updates and integrity checks from isolated directories. Local installation tests forbid download, npm and tar commands, and verify that missing dependencies or build output cause errors without writing the target.
- **Framework** (`test_framework.ts`): the library's loops and roles as each side's project gets them, the loop and role checks (child loops, loop kinds and drafts included), the hook actions, the check that every answer a loop gets is the owner's own, and the worker's ledger and waiting.
- **Contribution** (`test_contribution.ts`) models the three repositories on local bare repositories standing in for GitHub: the framework's library and the community's, each in its own repository, and this package with both as real submodules. It runs the real installer and git, with a stand-in `gh`. Sharing sends only what the project made, always to the community library. Sending upstream sends each improvement back to the library that gave it (this package's roles to this package, the framework's base roles to the framework), merged with what that library changed meanwhile, or holds it back as a conflict. Nothing leaves before a task has finished; keys, tokens and hidden paths are blocked; a role of the wrong side, a stale script, a name a library already has or a result the library check fails stays out; a plan changed since the owner approved it is refused, its digest binding both the plan and its purpose; and on the validator nothing leaves either way without its own check's pass on that digest. Also forks without write access, `gh` missing or signed out, a checkout without a remote, a default branch without a library, fetching a checkout for a project installed from an archive, and projects installed before baselines were kept.
- **Loop view** (`test_loop_view.ts`) installs a worker and a validator project with the real installer and checks what the owner's page shows (the loops with their kinds, `setup` and the side's `configure` among them; steps and their roles; the loops a loop runs as steps; parameter values; runs from the trajectory index, no transcript read), the page written as one file (its data cannot close its script, nothing loaded from elsewhere) and the served page (only its own address, read-only).
- **Studio** (`test_studio.ts`) checks the console's server: the one-time sign-in, what a stranger is refused, the flows it draws from the loops the project got from the library (steps, stages, groups, arrows back, ahead and out, parameters joined to their steps, the loops run as steps, such as setup's `configure` and a contribution's own check) and the quick search.
- **Studio authoring** (`test_studio_authoring.ts`) drives the chat against a stand-in `claude`: the request reaching `loop-authoring` with what the owner pointed at, the review note and the draft drawn when the loop waits, the reply passed on unchanged, and the end.

Review sessions are tested against a stand-in `claude` command. Do not add Claude Code authentication checks to tests. Report the difference between archive and helper verification and a real two-machine deployment with Claude Code. Never restart a running Claude Code background service or Paseo daemon to recover from a test timeout.
