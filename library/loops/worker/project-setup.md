# Project setup (worker)

## Purpose

Setting a worker project up, starting from what the owner needs. The loop settles which loop the project runs, reusing one that fits or having one built on the closest existing loop; has the owner set that loop's parameters together with the connection to the validator, on one configuration sheet; applies it; and prepares the machine. The owner starts it with `claude --agent worker-setup "<the requirement, or start>"`: the session runs as `worker-setup` and carries the owner's answers in. It starts no research.

## Inputs

- `requirement`: the owner's first message, verbatim.
- `answers`: the owner's replies so far, by review id; the session adds each one as it comes (see `running-loops.md`).

## Steps

1. **Requirement** — `worker-setup` reads the requirement and the owner's later words (`{action: "requirement", requirement, notes}`): when they say how this machine should work on the validator's task, it restates the requirement; otherwise it says what it needs to know, `owner-review` asks the owner (`review_id` `requirement:<round>`), and their words come back as `notes`.
2. **Find** — `loop-query` finds the task loop installed for this side that fits the requirement (`{action: "find-task-loop", requirement, side: "worker"}`).
3. **Choose** — when one fits or comes close, `owner-review` shows the requirement as restated and that loop, with its purpose, steps, roles and parameters (`review_id` `setup-loop:<loop>`). Approval takes the loop, with the parameter values shown; `revise` sends the requirement with the owner's words to step 4; `cancel` ends the loop.
4. **Build** — when none fits, or the owner wants something else: the child loop `loop-authoring` builds a worker task loop on the closest existing loop (`{description, side: "worker", kind: "task", answers}`), with the owner's review of the draft. Its waiting is this loop's waiting; when it ends without a loop, so does this one.
5. **Sheet** — `worker-setup` puts the loop into the configuration sheet, turns the owner's words into changes, fetches `task.md` from the validator once the connection is set, and refreshes the sheet (`{action: "sheet", loop, suggested, notes, reason}`); the first time, the parameter values the owner approved with the loop are its values (`suggested`). `owner-review` shows the whole sheet (`review_id` `sheet:<round>:<digest>`); approval is possible only when it has no open issue. `revise` sends the owner's words back to this step; `cancel` ends the loop.
6. **Apply** — `worker-setup` confirms the approved digest and applies it (`{action: "apply", digest}`). When the validator changed `task.md` meanwhile, or the apply fails, the sheet goes back to step 5 with the reason.
7. **Environment** — `worker-setup` creates the wiki, writes and runs the environment skill's scripts and writes the environment section (`{action: "environment", notes}`). When it needs facts only the owner has, `owner-review` asks (`review_id` `environment:<round>`).
8. **Check** — `worker-setup` runs the loop and role checks (`{action: "check"}`); each stale or defective loop is regenerated by the child loop `loop-authoring` (`{regenerate: <loop>}`), and the checks run again.
9. **Hand off** — `worker-setup` writes the report for the owner (`{action: "handoff", requirement, loop, applied, environment, incomplete, check}`), and the loop ends with it.

## Bounds

3 requirement rounds, 12 sheet rounds, 3 environment rounds, 4 regenerated loops.

## Waiting

Steps 1, 3, 5 and 7, and the child loop in step 4, wait for the owner: the loop returns `{waiting: "owner", review_id, question, document}`, and the session runs it again with the reply in `answers`.

## Triggers

- `record-trajectory`: every role that finishes leaves its trajectory.
- `guard-owner-answers`: every answer the session passes in is the owner's own message, typed after the loop stopped at that review; anything else is blocked before the loop runs.
