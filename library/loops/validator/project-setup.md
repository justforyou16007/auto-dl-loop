# Project setup (validator)

## Purpose

Setting a validator project up, starting from what the owner needs. The loop has `task.md` written with the owner when it is missing; settles which loop reviews each submission, reusing one that fits or having one built on the closest existing loop; has the owner set that loop's parameters together with the validation terms, on one configuration sheet; applies it, which freezes the benchmark; and prepares the machine. The owner starts it with `claude --agent validator-setup "<the requirement, or start>"`: the session runs as `validator-setup` and carries the owner's answers in. It reviews no submission.

## Inputs

- `requirement`: the owner's first message, verbatim.
- `answers`: the owner's replies so far, by review id; the session adds each one as it comes (see `running-loops.md`).

## Steps

1. **Requirement** — `validator-setup` reads the requirement and the owner's later words (`{action: "requirement", requirement, notes}`): when they say what this machine should validate, it restates the requirement; otherwise it says what it needs to know, `owner-review` asks the owner (`review_id` `requirement:<round>`), and their words come back as `notes`.
2. **Task** — `validator-setup` writes `task.md` from the requirement when it is missing, or revises it as the owner's words ask (`{action: "task", requirement, notes}`). When it wrote or changed it, `owner-review` shows it (`review_id` `task:<digest>`): the whole task the worker will get. Approval goes on; `revise` sends the owner's words back to this step; `cancel` ends the loop. A `task.md` the owner wrote and setup did not change needs no review.
3. **Find** — `loop-query` finds the task loop installed for this side that fits the requirement (`{action: "find-task-loop", requirement, side: "validator"}`).
4. **Choose** — when one fits or comes close, `owner-review` shows the requirement as restated and that loop, with its purpose, steps, roles and parameters (`review_id` `setup-loop:<loop>`). Approval takes the loop, with the parameter values shown; `revise` sends the requirement with the owner's words to step 5; `cancel` ends the loop.
5. **Build** — when none fits, or the owner wants something else: the child loop `loop-authoring` builds a validator task loop on the closest existing loop (`{description, side: "validator", kind: "task", answers}`), with the owner's review of the draft. Its waiting is this loop's waiting; when it ends without a loop, so does this one.
6. **Sheet** — `validator-setup` puts the loop into the configuration sheet, turns the owner's words into changes and refreshes the sheet (`{action: "sheet", loop, suggested, notes, reason}`); the first time, the parameter values the owner approved with the loop are its values (`suggested`). `owner-review` shows the whole sheet (`review_id` `sheet:<round>:<digest>`); approval is possible only when it has no open issue. `revise` sends the owner's words back to this step; `cancel` ends the loop.
7. **Apply** — `validator-setup` confirms the approved digest and applies it (`{action: "apply", digest}`): the benchmark is installed and frozen, the token created. When the apply fails, the sheet goes back to step 6 with the reason.
8. **Environment** — `validator-setup` creates the wiki, writes and runs the environment skill's scripts and writes the environment section (`{action: "environment", notes}`). When it needs facts only the owner has, `owner-review` asks (`review_id` `environment:<round>`).
9. **Check** — `validator-setup` runs the loop and role checks (`{action: "check"}`); each stale or defective loop is regenerated by the child loop `loop-authoring` (`{regenerate: <loop>}`), and the checks run again.
10. **Hand off** — `validator-setup` writes the report for the owner, with the command that runs the service and the connection the worker needs (`{action: "handoff", requirement, loop, applied, environment, incomplete, check}`), and the loop ends with it.

## Bounds

3 requirement rounds, 6 task rounds, 12 sheet rounds, 3 environment rounds, 4 regenerated loops.

## Waiting

Steps 1, 2, 4, 6 and 8, and the child loop in step 5, wait for the owner: the loop returns `{waiting: "owner", review_id, question, document}`, and the session runs it again with the reply in `answers`.

## Triggers

- `record-trajectory`: every role that finishes leaves its trajectory.
- `guard-owner-answers`: every answer the session passes in is the owner's own message, typed after the loop stopped at that review; anything else is blocked before the loop runs.
